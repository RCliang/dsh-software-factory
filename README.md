# 软件工厂

DeepSeek Harness 插件。给已经存在的项目加功能或修 bug：先调查和澄清，再分别批准需求和计划，然后串行改代码、自验、独立评审、用户验收。提交、推送、合并、发布仍然是四次分开的人工确认。

这是 v1。它不并行调度，不自动提交、推送、合并或发布，也不清理已有的未提交改动。

## 安装

在装有 `dsh` 的机器上，从本仓库目录安装到 Web profile：

```sh
dsh plugin --profile web add ./
dsh --profile web --dump-config
dsh --profile web
```

从 Git 安装时，把 `./` 换成 `github:RCliang/dsh-software-factory#<40位commit>`。pnpm 10 起，Git 依赖的安装脚本需要你在 profile 的 `pnpm-workspace.yaml` 里显式允许；本包的运行入口是已经放在仓库里的 `lib/`，没有 `prepare` 脚本。

卸下：

```sh
dsh plugin --profile web remove dsh-software-factory
```

`package.json` 的 `engines.dsh` 写成 `>=0.1.0-rc.6`。这个范围没有在本仓库的环境里用真实 `dsh` 安装验证过。

## 打开工作台

启动 Web UI 后，在左侧栏点 **软件工厂**。

这一项注册在官方根级 `sidebar.panellist`，id 是 `software-factory`。中间页面注册在根级 keyed slot `main` 的同一个 key。官方壳仍然是侧栏、主区和右侧栏；工厂自己的顶栏、任务流和工作面画在这个 main 页面里面，没有另做 DOM 槽。

布局选择在刷新后会丢掉，这是官方 layout 的限制。运行状态放在 `ctx.storageDomain` 的 `software_factory` 域里，不放在布局状态里。

如果目标 DSH 拒绝这个 main 注册，本包不会去改内部 DOM。那种环境需要先核对 slot，再决定要不要降级成确认卡片。

## 跑一遍

1. **开始。** 写下要做什么。时间额度由你填写分钟数。花费额度只能选「这次不设费用上限」或写一句话，插件不编造金额。建议默认是每个任务最多自动返修 2 轮，确认前可以改。工作区若有未提交文件，先列出摘要，再选「先处理这些改动」「允许在现有改动上继续」或「取消」。额度、建议默认和脏目录没处理完，不能开始调查。
2. **调查。** 只记录已查证事实、推测和可能影响的位置。调查没完成不能提问，也不能改代码。
3. **澄清。** 每次最多两个问题，并写明为什么代码里查不到。可以直接改需求草稿。
4. **需求确认。** 批准的是具体 Spec 版本。有未决项时默认不能进入计划，除非明确允许带着未决项继续。没写必须保留的既有行为，不能批准。
5. **计划确认。** 每个任务要有文件范围、依赖、验收编号和验证命令。重构或既有行为变化必须和需求分开确认，并写明对既有行为的影响。小改可以一次确认，界面仍分成两块。批准计划之后才允许写当前任务范围内的文件。
6. **开发与自验。** 一次只做一个任务。失败要分成环境故障、开工前就有的失败、这次引入的失败，或尚未覆盖。这次引入的失败会自动返修，超过上限就停在现场。
7. **独立评审。** 只把已批准且未失效的 Spec、Plan、真实 diff 和验证证据交给评审。开发总结不会放进评审提示。评审要配置一个不继承父上下文的 `agentPreset`，以及父会话 id。派发失败不会被记成通过。
8. **用户验收。** 测试通过不能代替你点「验收通过」。
9. **四次确认。** 验收之后依次是提交、推送、合并、发布。每一次只记录这一步，按钮不能互相代替。插件不执行 `git commit`、`git push`、合并或发布。

暂停会停住后续写入，现场还在。取消只停止后续执行，工作区改动保留。

重新打开时，插件按存储里的运行恢复：已完成且文件范围没变的任务不会重做；需求或计划若已失效，不会拿草稿或旧计划继续写代码。
